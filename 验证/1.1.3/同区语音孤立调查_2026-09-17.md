# BVF 1.1.3 同区语音孤立调查

## 结论

已确认本机进入独立语音房，重连后仍孤立。BVF 现有重连管理和 UI 判定存在缺陷，但首次分房的原因尚未确定，不能归因于 1.1.3 新增的 VoiceStateRecovery。

## 最近改动核对

NetworkManager、RegionControl、Patches、PhotonRPCFix 与 1.1.1 备份全文相同；上述文件及 RoomCodePatches、InviteHandshake、InviteRoomNameEncodingPatch 与新增静音恢复前 1.1.2 备份全文相同。1.1.3 的 VoiceStateRecovery 不调用连接、断开或改语音服务器参数；跳过本地角色，只恢复失效的远端 CharacterData 引用。

本机配置自动选区，手动重连开启，中文生效的虚拟玩家开关为 false；没有修改配置。

## 已定位的代码问题

1. **双重重连管理**：NetworkManager:1105/1225 直接 Client.Disconnect，绕过 VoiceFollowClient.Disconnect 的 manualDisconnect 标志。当前游戏原版在 OnVoiceStateChanged 收到 Disconnected 后也会 FollowLeader/ConnectVoice；BVF 的 ProcessPendingReconnect 又等待底层断开并发起 ConnectVoiceNow，存在竞争。默认自动跟随开启时可由原版先抢走连接流程。
2. **目标 IP 只是比较条件**：NetworkManager:737 的 ConnectVoiceNow 复制设置、绑定游戏区服，然后常规匹配；它不使用 TargetGameServer 定向连接。重试不保证改变导致分房的参数。不能把“跟随房主 IP”的决策文案当作实际路由保证，也不应反射硬写 GameServerAddress。
3. **孤立不直接触发纠正**：SingleReport 只用于显示，不被 DecideTargetIP 采用；盲连分支只处理 Disconnected，已经 Joined 的孤立客户端会停留。收到可信房主/多数派地址后最多纠正两次，WrongIPCount 到 3 后妥协停止。
4. **面板误导**：VoiceUIManager:509–518 将不同 IP 统一分类为 Abnormal，Localization 显示“跨区”，即使两端都 hk。1129 的“无法判断队友”兜底只看本机有无 IP，不包含孤立，故会把不在本机语音房的队友写成“未连入语音服”。
5. **日志漏关键证据**：BroadcastLog:495 只进 UI 和房间事件，不写 BepInEx 文件；重连决策、原因、超时、按键细节没有落盘。TrackDiagnostics:1040 将断开时的 0 人状态写成“孤立解除”，不能代表恢复成功。

## 当前原版核对

按索引检查后新增 PEAK 2.4.c 的 PunVoiceClient、VoiceFollowClient、VoiceConnection、VoiceClientHandler 定向归档，已更新反编译索引。原版 PunVoiceClient.ConnectVoice 默认路径与 BVF ConnectVoiceNow 的设置复制基本一致，未发现原版另行补写 AppVersion 而 BVF 漏写的证据；不能凭猜测将 AppVersion 定为根因。

Photon 官方匹配指南要求核对 Region、AppId 和 AppVersion；同区域与房名不构成完整匹配身份。当前日志缺少语音运行时 AppId/AppVersion/CurrentCluster 和对端对应值，因此不能确定首次分房是哪一项造成。

参考：https://doc.photonengine.com/pun/current/lobby-and-matchmaking/matchmaking-and-lobby

## 建议实现范围（本次尚未实施）

- 主动恢复由单一状态机控制，断开使用原版带 manualDisconnect 的接口；每轮记录发起方、原因和连接返回值。
- 加入精简的一次性连接参数诊断：语音 AppId/AppVersion/region/cluster、房名、服务器地址、房内人数，与房主/多数派实际值比较。不要记录认证令牌。
- 先据参数差异处理匹配问题，避免只重复同一连接；没有足够证据时明确告知无法定向恢复，不把 Joined 当作已恢复可通话。
- 修正“同区不同服务器”“本机孤立、队友状态无法判断”和“断开中”的显示。
- 保留 1.1.3 语音状态引用恢复，当前没有证据支持为此回滚它。
